================================================================================
SECTION 1: CORE PRINCIPLES (NON-NEGOTIABLE)
================================================================================

Every AI-assisted development session MUST enforce these principles:

PRINCIPLE 1: EVIDENCE BEFORE CLAIMS
- No feature may be marketed or documented as operational until it has
  Class A (implemented + regression-covered) or Class B (controlled harness)
  evidence.
- The credibility regression suite must pass before any public-facing text
  is updated.
- The 4-tier evidence taxonomy (A/B/C/D) governs ALL claims.

PRINCIPLE 2: FAIL-CLOSED SECURITY
- Every containment action requires: human approval → HMAC-signed audit →
  adapter verification → rollback capability.
- Missing or invalid approval/audit evidence MUST prevent execution.
- No code may bypass approval gates, omit audit records, or hardcode secrets.

PRINCIPLE 3: DETERMINISTIC BEFORE PROBABILISTIC
- Build deterministic correlation rules, fixtures, and MITRE mappings FIRST.
- AI/ML features (Class D) must not be presented as operational (Class A).
- All AI suggestions must be evidence-grounded, explainable, and human-reviewed.

PRINCIPLE 4: OPERATIONAL REALITY
- Every service must be deployable, observable, and recoverable.
- No stub services in production topology. Consolidate or implement.
- All code must pass: isolated regression → Docker Compose validation →
  controlled external lab gate before production claim.

PRINCIPLE 5: SECRET-FREE SOURCE
- Runtime credentials via environment variables ONLY.
- No secrets in source code, Docker images, or git history.
- Use .env.example for documentation, never .env with real values.

================================================================================
SECTION 2: EVIDENCE TAXONOMY (MUST BE ENFORCED BY AI)
================================================================================

Before implementing ANY feature, classify it:

| Class | Meaning | AI Action |
|-------|---------|-----------|
| A — Implemented & regression-covered | Source code + deterministic tests | Implement, test, document as operational |
| B — Controlled harness evidence | Mocked/SQLite/LocalStack/disposable proof | Implement with harness, document boundary |
| C — External lab required | Needs real dependency/host/device/operator | Build protocol, schedule lab, document as pending |
| D — Roadmap / intentionally unsupported | Not currently operational | Add to ROADMAP.md, block from public claims |

AI MUST reject any request to:
- Promote Class D to Class A without evidence
- Add unsupported phrases to public-facing files (README, website, docs root)
- Skip regression tests for "production-ready" features
- Hardcode secrets or disable approval gates

SECTION 5: AI DEVELOPMENT WORKFLOW INSTRUCTIONS
================================================================================

When using Manus AI / Cursor / Claude Code for development, follow this
workflow for EVERY task:

STEP 1: TASK CLASSIFICATION
- Ask: "What evidence class does this task target?"
- If Class A: Proceed with implementation + regression tests
- If Class B: Proceed with implementation + harness tests
- If Class C: Build protocol first, schedule lab, implement with mocks
- If Class D: Add to ROADMAP.md, implement only if explicitly requested

STEP 2: IMPLEMENTATION CHECKLIST
Before writing code, verify:
- [ ] No hardcoded secrets
- [ ] Environment variables documented in .env.example
- [ ] pydantic-settings validation configured
- [ ] /health, /ready, /metrics endpoints planned
- [ ] Error handling for all external dependencies (fail-closed)
- [ ] Audit logging for all state-changing operations
- [ ] Tenant isolation validation
- [ ] Regression tests planned

STEP 3: CODE REVIEW PROMPT
After implementation, run this checklist:
- [ ] Does this code bypass any approval gate? (REJECT if yes)
- [ ] Does this code omit audit records for state changes? (REJECT if yes)
- [ ] Are there hardcoded credentials or keys? (REJECT if yes)
- [ ] Does this code handle missing dependencies gracefully? (SAFE_MODE)
- [ ] Are all external calls bounded by timeouts and retries?
- [ ] Is tenant scoping validated on every data access?
- [ ] Are error messages safe (no sensitive data leakage)?

STEP 4: TESTING REQUIREMENTS
- [ ] Unit tests with mocked dependencies
- [ ] Integration tests with SQLite/LocalStack
- [ ] Regression test added to isolated suite
- [ ] Docker Compose validation (service starts, health passes)
- [ ] If Class B/C: Protocol document updated with test procedure

STEP 5: DOCUMENTATION REQUIREMENTS
- [ ] API documentation updated (OpenAPI/Swagger)
- [ ] Architecture docs updated if service boundaries changed
- [ ] Operations guide updated for new feature
- [ ] Public claims reviewed against evidence taxonomy
- [ ] CHANGELOG.md updated with evidence class

STEP 6: CREDIBILITY REGRESSION
Before any commit touching public-facing files:
- [ ] Run claim regression suite
- [ ] Verify no unsupported phrases in README, website, docs root
- [ ] Verify MITRE mappings are accurate
- [ ] Verify no "autonomous," "self-healing," "blockchain," "post-quantum"
      language without evidence reclassification

SECTION 8: EMERGENCY PROCEDURES
================================================================================

If Manus AI or any tool generates code that:

1. BYPASSES APPROVAL GATES
   → Revert immediately
   → Add regression test preventing the bypass
   → File incident report in docs/INCIDENTS.md

2. ADDS UNSUPPORTED CLAIMS TO PUBLIC FILES
   → Revert the text changes
   → Run credibility regression suite
   → Review why the suite didn't catch it

3. INTRODUCES HARDCODED SECRETS
   → Rotate the secret immediately
   → Scrub from git history (git-filter-repo or BFG)
   → Add pre-commit hook preventing recurrence

4. BREAKS FAIL-CLOSED BEHAVIOR
   → Revert immediately
   → Add test verifying fail-closed on dependency outage
   → Document the failure mode
